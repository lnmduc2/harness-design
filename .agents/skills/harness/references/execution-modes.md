## 1. Mode A: Workflow Orchestration

Executes orchestration scripts via the `Workflow` tool. Control-flow constructs such as fan-outs, loops, and conditional branches are governed deterministically by **code** rather than per-turn model judgment. Consequently, identical inputs yield identical execution structures, making it ideal for running large numbers of agents in parallel.

```
[Main Agent] → Workflow(script)
           ├── phase('Explore'): pipeline(items, item => agent(...))
           ├── phase('Verify'): Search for refuting evidence per discovered item (parallel)
           └── return { confirmed }   ← Structured final deliverable
```

**Key Capabilities:**
- `agent(prompt, opts)` — Dispatches a subagent. When `opts.schema` defines a JSON Schema, it returns a schema-validated structured object. No manual parsing is required, and validation mismatches trigger automatic retries. Specifying `opts.agentType` invokes custom agent types defined in `.claude/agents/`. Fine-tune reasoning effort with `opts.effort`, and isolate file changes with `opts.isolation: 'worktree'`.
- `pipeline(items, stage1, stage2, ...)` — Processes each item independently through sequential stages. Because there is no synchronization barrier between stages, **use this as the default for multi-stage pipelines.**
- `parallel(thunks)` — A synchronization barrier that waits for all tasks to complete. Use only when downstream stages require the **entire** batch of results from prior stages (e.g., global deduplication or early termination based on aggregate counts).
- `phase(title)` / `log(msg)` — Groups progress logically and communicates current activity to the user.
- `budget` — Integrates with user-specified token budgets (e.g., "+500k"). Use `budget.total` and `budget.remaining()` to dynamically adjust execution scale.
- `workflow(nameOrRef, args)` — Nests workflow executions up to one level deep. Used for hierarchical delegation.

**Characteristics:**
- Code dictates control flow, ensuring identical inputs follow identical execution paths.
- Structured output (`schema`) enables passing validated, type-safe data between stages.
- `resumeFromRunId` enables resuming interrupted runs. Unchanged `agent()` calls return cached results immediately, drastically reducing re-run costs.
- Runs in the background and delivers notifications upon completion.

**Constraints:**
- **Requires explicit user initiation.** Allowed only if the user explicitly requested a workflow/multi-agent orchestration, or invoked a skill that instructs `Workflow` execution. Orchestration skills generated by Harness fulfill the second condition. However, keep default agent counts conservative, reserving massive sweeps only for explicit user requests.
- Scripts must be written in pure JavaScript; TypeScript syntax is not permitted. Dynamic non-deterministic functions like `Date.now()`, `Math.random()`, or argument-less `new Date()` are forbidden because they prevent run resumption. Pass timestamps via `args`.
- The `meta` block must contain only literal values. Variables, function calls, and spread syntax are not permitted.
- Concurrency limits apply to parallel agents per session. Tasks exceeding the limit are automatically queued. An overall ceiling on total agent calls per workflow prevents runaway loops.
- Failed or skipped `agent()` calls return `null`. Because `parallel()` does not throw exceptions upon task failure, always filter results with `.filter(Boolean)`.
- The `parallel()` barrier only synchronizes completion time; it does not prevent subsequent edits. In hybrid modes, persistent agents woken via `SendMessage` after a workflow phase could inadvertently modify that phase's artifacts; therefore, freeze deliverables at mode boundaries (Phase 4 of Template B in `orchestrator-template.md`).

**Well-suited Tasks:** Fan-out across enumerable lists (e.g., N files or M perspectives), loop-until-dry iterations, adversarial verifications, large-scale migrations and audits, and structured report synthesis.

**Ill-suited Tasks:** Tasks where items cannot be enumerated in advance because scope must be discovered interactively through dialogue, or tasks requiring frequent mid-flight consultations with the user.

> For concrete script boilerplate and gotchas, refer to `workflow-recipes.md`.

## 2. Mode B: Persistent Agent Collaboration

Spawns named agents and coordinates them via a shared task list and `SendMessage`. This replaces the v1 "Agent Teams" mode.

**Major Difference from v1:** `TeamCreate` and `TeamDelete` no longer exist. Unlike v1, no explicit team object is created; agents launched with names in a session automatically belong to a shared collaborative context.

```
[Main Agent (Leader)]
    ├── Agent(name: "researcher", subagent_type: "...", prompt: ...)   ← Parallel execution
    ├── Agent(name: "critic", ...)
    ├── TaskCreate(tasks + dependencies) → Shared task list
    ├── SendMessage({to: "researcher"}, ...)  ← Follow-up instructions preserving conversational context
    └── Receive completion notification → Aggregate findings → Final synthesis
```

**Key Capabilities:**
- `Agent(name: ..., subagent_type: ..., model: ..., prompt: ...)` — Assigning `name` creates a persistent agent addressable via `SendMessage`. Runs in the background by default and sends a notification upon completion. Set `run_in_background: false` if synchronous waiting is required.
- `SendMessage({to: name})` — Instructs a previously launched agent to continue working **while preserving conversational context**. Essential for iterative review and revision loops.
- `TaskCreate` / `TaskUpdate` / `TaskList` / `TaskGet` — Shares task state across agents. Manages task dependencies and execution progress, enabling supervisors to dynamically allocate tasks based on status.
- `TaskStop` — Halts background tasks that are stuck in runaway loops or no longer necessary.

**Characteristics:**
- Agents retain historical context, allowing them to handle follow-up requests like "Revise only Section 2 of the draft created earlier in this session."
- Agents can share intermediate findings, debate conflicting perspectives, and adjust trajectories dynamically.
- Specialists remain available throughout the lifetime of the session.

**Constraints:**
- The main agent (leader) coordinates directly; as agent count increases, the leader becomes a coordination bottleneck. Lean teams of 3–5 agents are recommended.
- Deeply nested delegation layers increase latency and degrade conversational context. Keep delegation within two tiers.
- Consumes more tokens than one-shot subagent calls.
- Because named agents continue receiving messages even after reporting completion, they might edit previously finalized artifacts in response to late questions from other agents. If downstream stages rely on those artifacts, freeze deliverables at stage boundaries. Follow the freezing procedure in Phase 4 of Template B in `orchestrator-template.md`.

**Well-suited Tasks:** Iterative author-reviewer revision loops, resolving discrepancies across contradictory datasets via discussion, dynamic task allocation by a supervisor, and workflows requiring dedicated specialists across an entire session.

**Ill-suited Tasks:** Fire-and-forget one-off tasks, or large-scale enumerable fan-outs where control flow can be pre-scripted.

## 3. Mode C: Sub-agent Delegation

Delegates one-off tasks via individual `Agent` tool invocations. Only the final result returns to the main agent; subagents do not communicate with each other.

```
[Main Agent] → Agent(Subagent A) ─┐
             → Agent(Subagent B) ─┼→ (Parallel, background by default) → Completion notification → Aggregate results
             → Agent(Subagent C) ─┘
```

**Characteristics:**
- Lightweight and fast with minimal coordination overhead. The main agent receives concise summary results.
- Independent calls batched within a **single message turn** execute concurrently.
- Executes in the background by default. Specify `run_in_background: false` if immediate inline results are needed.
- The main agent avoids redundant searches while waiting for delegated results.

**Constraints:**
- Agents cannot communicate with each other, and conversation context terminates once the call concludes. To start fresh without retaining state, invoke without `name`.
- All aggregation and coordination fall squarely on the main agent.

**Well-suited Tasks:** One-off investigations and data collection, specialist dispatch where only the final outcome matters, and single-pass independent verifications.

**Ill-suited Tasks:** Tasks requiring multi-turn iterative negotiation, or large-scale fan-outs that can be orchestrated deterministically via code.

## 4. Decision Tree for Execution Mode Selection

```
Can the task list, verification criteria, and iteration conditions be expressed in code beforehand?
├── Yes → Workflow Orchestration (Mode A)
│         Control flow is governed deterministically by code, not per-turn model judgment.
│         Ensure explicit user initiation criteria are met and do not inflate agent counts unnecessarily.
│
└── No → Does iterative dialogue and context retention between agents improve deliverable quality?
          ├── Yes → Persistent Agent Collaboration (Mode B)
          │
          └── No → Are there two or more agents?
                        ├── Yes → Sub-agent Parallel Delegation (Mode C)
                        └── No → Sub-agent Single Call (Mode C)
```

**Hybrid Modes:** When different phases yield different answers to the decision tree, combine execution modes. Common pairings include:

| Combination | Flow | Example |
|---|---|---|
| Workflow Collection → Persistent Integration | A → B | Fan out massive data collection via Workflow; resolve discrepancies and reach consensus via persistent agent discussion |
| Persistent Generation → Workflow Verification | B → A | Draft initial deliverables with a persistent team; fan out adversarial verification for each finding via Workflow |
| Sub-agent Pre-investigation → Workflow Execution | C → A | Survey scope with subagents to establish the item list, then pass that list via `args` into a Workflow |

**Pre-orchestration Scope Confirmation:** Prior to launching a workflow, briefly survey files, review targets, or audit items to lock down the exact task list. Determining scope upfront simplifies scripts and avoids wasteful redundant execution.

## 5. Migrating from v1 to v2

When encountering legacy v1 orchestrators or agent definitions, migrate them to v2 according to the table below:

| v1 Construct | Status | v2 Replacement |
|---|---|---|
| `TeamCreate(team_name, members)` | **Removed** | Dispatch `Agent(name: ...)` in parallel in a single message turn. Named agents belong automatically to the session's collaborative context; no dedicated team object is required. |
| `TeamDelete` / "Team Cleanup" Phase | **Removed** | Delete the phase entirely. Agents conclude naturally when tasks end, or can be halted via `TaskStop` if needed. |
| "Only one active team per session" limit | **Restructured** | With the removal of explicit team objects, this restriction no longer applies. Named agents collaborate naturally within the session. |
| `SendMessage({to: "all"})` Broadcast | Replaced | Send individual `SendMessage` calls only to intended recipients. |
| `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1` | **Obsolete** | Remove from all documentation, environment settings, and scripts. |
| Blanket `model: "opus"` pin on all agents | Deprecated | Select models based on task characteristics. Use `sonnet` when uncertain, and retain model inheritance only when deliberately chosen. |
| Large-scale fan-outs built as teams | Improved | Migrate to `Workflow` scripts. Enforce control flow in code, utilize structured output schemas, and leverage run resumption. |
| Orchestrator "Phase 0: Context Audit" | Retained | Retain existing procedure, adding the `resumeFromRunId` option for workflow orchestration modes. |
| `_workspace/` file conventions | Retained | Keep as standard practice. |
| `CLAUDE.md` pointers and change history | Retained | Keep as standard practice. |

**Migration Procedure:**
1. Remove `TeamCreate`, `TeamDelete`, broadcast calls, and experimental flags from legacy orchestrators.
2. Identify fan-out and verification loops. If control flow can be determined in code, convert those stages to Workflow Orchestration.
3. Rewrite remaining collaborative stages using Persistent Agent Collaboration syntax (`Agent(name:)` + `SendMessage` + `TaskCreate` / `TaskUpdate`).
4. Remove blanket `model: "opus"` pins from agent definitions, preserving explicit model tiers only with justified rationale.
5. Re-run Phase 6 verification (structural checks and dry runs) and record updates in the `CLAUDE.md` change history.
